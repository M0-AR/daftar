Shipping Daftar to paying users on Windows, macOS and Linux

Goal: a buyer downloads one installer, double-clicks it, and is asking questions about their documents within minutes, with no terminal, no second program to install, and no security warnings. Researched 2026-11-10; every decision below cites a source or a local measurement.

1. The engine: bundle llama.cpp instead of requiring Ollama

Why. Requiring a separate Ollama install is the largest source of support pain: "requires a newer version of Ollama" (HTTP 412) is reported as the most common Ollama failure, minimum versions per model are undocumented, and updated clients often keep talking to an old server (ollama #14431, #13411, #18414). On this machine Ollama 0.23.2 silently ran CPU-only, could not run Qwen3.5 or PaddleOCR-VL, and crashed on an image (docs/RESEARCH.md #19, #20, #22). The products users already trust ship the engine inside the app: Jan bundles llama.cpp (CUDA 13 + Vulkan), LM Studio ships a llama.cpp runtime, and AnythingLLM replaced its bundled Ollama with llama.cpp (Jan docs, promptquorum).

What. Bundle the official llama-server (MIT) and run it as a private child process on a loopback port, exactly like Daftar's own server. It provides chat, embeddings, reranking (/v1/rerank, which Ollama lacks) and vision via --mmproj (llama-server README). Single-user speed is equal or 5-15% better than Ollama (InventiveHQ).

CUDA builds are faster on NVIDIA but cost 163 MB + 407 MB runtime per install; offer them later as an optional "NVIDIA speed pack". Lesson from Jan's bug (jan #9091): never pick a backend from a table; probe it (llama-server --list-devices) and fall back to CPU if the GPU backend fails to load. Keep Ollama support as an "advanced: use my own Ollama/llama-server" option, as Jan does.

Built 2026-11-13 (Phase 1b). daftar/llama_server.py starts llama-server on a loopback port, auto-discovers binaries under ~/models/llama.cpp/** and models under ~/models/** (explicit paths in Settings), tries the GPU build before CPU, waits for /health (180 s), and stops the child on exit. Status and setup read file metadata without loading the model (~0.02 s); the server starts on the first question. Verified on Linux with b12360 Vulkan (RTX 3090) and CPU builds: model load <1 s, smoke answer 1.1 s end-to-end, keyword search and [n] citations work, process cleaned up after shutdown. Trap: a stale system llama.cpp (here /opt/llama) wins over the binary's RUNPATH and crashes it, so the launcher prepends its own directory to LD_LIBRARY_PATH (macOS DYLD_LIBRARY_PATH, Windows PATH). Win/Mac launching is implemented but untested. Embeddings/OCR for this engine are not wired yet (keyword-only search; scans are reported unreadable), and the nightly build is not pinned for distribution yet.

Hardened 2026-11-13 after a full re-audit. The child now gets a random API key (LLAMA_API_KEY; the client sends it, /health stays public: measured 401 without it). A pid file stops orphans after a crash on Linux/macOS (the command line must still name the model; a live parent means another Daftar owns it) and via PowerShell CIM on Windows; any lookup failure means "never kill". Logs rotate at 5 MB. Shutdown moved to FastAPI's lifespan (Starlette 1.x removed event handlers; FastAPI's shim is legacy), the UI is served Cache-Control: no-store, and embedding-only .gguf files are no longer offered as chat models. scripts/build.py bundles vendor/llama.cpp when present as data, not binaries, so PyInstaller does not rewrite the engine (it keeps the executable bit when the source has it). A notarized macOS app must collect the engine as a binary under Contents/Frameworks in Phase 4; data-only directories are cross-linked there, so discovery works, but code in Contents/Resources breaks the signature. Verified: 114 offline + 3 live tests, API-key auth end-to-end, think-off first token 0.05 s vs think-on 0.4 s.

2. Models: download on first run, sized to the machine, commercially licensed

  • Licences for a paid product. Qwen3 / Qwen3.5 / Qwen3-Embedding and PaddleOCR-VL are Apache 2.0; Gemma 4 is Apache 2.0; Gemma 1-3 (our current default gemma3:1b) use the custom Gemma Terms, which require passing the use restrictions down to every customer (promise.legal, Gemma 4 Apache, Qwen3 Apache, PaddleOCR-VL licence). → Default to Apache-2.0 models; choose between Qwen3.5-2B and Gemma 4 E2B with scripts/eval_answers.py.
  • Size by hardware. Detect RAM and VRAM; recommend a model that fits weights + KV cache, because spilling to system RAM can be ~30x slower (promptquorum VRAM tiers). Rough tiers: ≤8 GB RAM / no GPU → 1-2B; 4-6 GB VRAM → 3-4B Q4; 8-12 GB → 7-14B Q4; 24 GB → up to ~30B Q4. Show a green/yellow/red "fits" badge like LM Studio.
  • Downloads. Resumable, SHA-256 verified, with a mirror fallback (Jan added a backup CDN after GitHub failures, Jan v0.6.10). A "use files I already have" button imports GGUFs from disk (offline installs, slow connections).
  • Default set: chat (~1.3 GB) + search Qwen3-Embedding-0.6B (639 MB) + OCR PaddleOCR-VL (optional, ~1 GB).

3. Installers, signing and the window

Windows macOS Linux
Package Inno Setup installer (per-user, no admin) signed + notarized .dmg AppImage (+ .deb)
Web view WebView2: present on Windows 11 and most Windows 10; check the registry and run Microsoft's 2 MB bootstrapper only if missing (Microsoft) WKWebView, built in WebKitGTK is the fragile one: use the system webkit2gtk-4.1 ("thin AppImage") and open in the browser if it is missing (pywebview #1818, briefcase #1029)
Signing Azure Artifact Signing, $9.99/month; EV certificates no longer skip SmartScreen, reputation builds per publisher (Microsoft, gdgsoft) Apple Developer ID, $99/year; hardened runtime + entitlements allow-unsigned-executable-memory (PyInstaller needs it), sign inside-out, notarize, staple (dev.to, pyinstaller #4629) none needed; publish SHA-256 sums

Without signing, Windows shows "Windows protected your PC" and macOS refuses to open the app, the two most common reasons buyers uninstall.

Updates: tufup (TUF-signed, patch-based updates for PyInstaller apps; PyUpdater is discontinued) (tufup). Always ask before updating, and keep the previous engine version for rollback (Jan users complained when they could not roll back, jan #9177).

4. First-run experience (the 5-minute promise)

  1. Welcome: what Daftar does, that nothing leaves the computer.
  2. Hardware check (automatic): CPU, RAM, GPU + backend that actually loads; plain-language result.
  3. "Recommended for this computer": one button downloads the fitted set, with progress, pause and resume; or "I have model files" to import.
  4. Smoke test: one tiny question to the model; show the speed. If it fails, fall back (GPU → CPU) and say so.
  5. Create the first collection with drag and drop. Every failure screen states the cause and one action ("Your graphics driver is too old for GPU mode; Daftar is using the processor. Update the driver to make it about 10x faster").
